# Limitations and truthful boundaries

1. No coding system can guarantee that a natural-language product idea is complete or internally consistent.
2. “One shot” can remove operator-managed engineering iteration; it cannot safely infer every irreversible product decision.
3. Model-generated architecture and code remain probabilistic.
4. Passing tests only proves what the tests and runtime demonstrations cover. Manageroo requires each product acceptance outcome to bind to specific proof gates; a green unrelated test cannot prove a different promise.
5. The built-in context token estimator is conservative character-based estimation, not a provider tokenizer.
6. A supported live coding-agent adapter must be installed and authenticated. Controlled runs currently support Codex; Claude Code, Gemini, and custom generic processes are refused because provider approval flags do not prove a host filesystem boundary.
7. Automatic selection is currently Codex-only. Manageroo does not bypass a safety decision by switching models.
8. Codex's native sandbox is required in addition to Manageroo's transactional attempts, read-only immutability, changed-file scope, Git ownership, verification, review, and completion evidence.
9. Native Windows Manageroo runs are not supported by the current secure artifact backend. Windows users run Manageroo inside WSL2; the PowerShell installer fails with that instruction instead of advertising a runtime that cannot construct the controller.
10. Failed configured worker attempts are rolled back to their pre-attempt Git checkpoint. A successful read-only worker that mutates its repository is rejected and rolled back. On `run --continue`, uncheckpointed workspace dirt is discarded while controller-owned verified checkpoints are retained.
11. The isolated mirror excludes Git-ignored files. Applications that require ignored generated assets, dependency trees, local secrets, or machine-specific state must provide them through a controlled reproducible environment. Manageroo intentionally does not copy ignored secrets or arbitrary local state into the isolated workspace.
12. Symlinks are excluded from the mirror in the current implementation to prevent path escape.
13. Independent map and review chunks can run in parallel. Implementation tasks remain dependency ordered for correctness.
14. Media support is bounded support. MANAGEROO records images, PDFs, and design/media assets in inventory and can use configured document/media evidence lanes, but it does not perform real vision interpretation or design understanding. It does not pretend metadata alone is real visual understanding.
15. Long prose support includes line counts, summaries, document manifests, optional `document_analysis_command` output, explicit summary context, and task decomposition. Exact edits still require bounded line ranges or an external document-specific command that owns the evidence.
16. GBrain, GitNexus, Clawpatch, AUTOREVIEW, and Obsidian integrations require local configuration and are not silently installed. An explicitly requested GBrain or document/media lane is required during direct `run` as well as readiness; missing or failed commands block instead of being mislabeled optional. When the user selects the recommended stack, TruffleHog is installed automatically only because AUTOREVIEW requires it; the official release archive is pinned and checksum-verified, and existing user-owned copies are reused.
17. Obsidian search and export require Linux `openat2` beneath/no-symlink resolution and fail closed on kernels or platforms that do not expose that containment primitive. Vault and export directories must be owned by the current user and not writable by another account; a writable private primary group containing only that user is accepted. Export directory chains must already exist, and export refuses to overwrite an existing file, because recursive creation and destructive replacement cannot preserve the same containment guarantee under concurrent namespace mutation. Another process running as the same account has equivalent filesystem authority and remains outside this containment boundary.
18. Configured AUTOREVIEW and Clawpatch commands are deterministic command-owned lanes. MANAGEROO captures their output and can accept their scoped edits, but it does not ask the AI repairer to freehand fixes from their findings.
19. `solo --create` creates only missing or empty top-level project folders. Starters are small local scaffolds, not production frameworks. The command refuses non-empty non-Git folders and missing paths inside another Git repo. Existing Git repositories must have a clean index and worktree, no tracked paths, and no entries outside `.git`; the scaffold commit stages only files it created so it does not accidentally commit personal files, secrets, archives, nested repositories, or unrelated deletions.
20. MANAGEROO does not replace CI, production monitoring, backups, security review, or legal review.
21. `release-ready` is a final operator gate, not a deployment tool. It checks readiness, a completed Manageroo run, approved review, final report, final patch, applied-to-source status, gates, clean Git state, target, rollback notes, and approval, then writes `.manageroo/cache/production-handoff.md`. Verification gates run in a disposable exact-HEAD clone, so ignored dependencies or machine-only files in the operator checkout are unavailable unless a gate recreates them. Any HEAD, tracked, untracked, or ignored mutation made by one gate rejects the release before a later gate runs. A ready handoff authorizes a tar archive generated from the locked exact commit, records its SHA-256, and tells the operator not to deploy the mutable source worktree. It does not push, deploy, monitor, or roll back production.
22. MANAGEROO does not run cloud schedules or timer loops by itself. Loop and routine patterns are adapted into bounded local goal-style runs unless the operator supplies a separate scheduler.
23. The learning lane records suggestions and can approval-apply low-risk project-memory notes. It does not silently edit skills, docs, config, installer behavior, checks, prompts, or code.
24. High-risk migrations, billing, authentication, authorization, destructive data operations, and regulated workflows should still require human approval before production deployment.
25. `run --continue <run-id>` continues Manageroo's saved worker job queue from disk. It replays the controller from saved artifacts and job records; it is not a terminal keepalive feature and does not promise that a killed OS process kept running.
26. Stateless worker orchestration reduces dependence on chat memory and compaction. It does not make probabilistic model output deterministic; it records packets, attempts, artifacts, checks, failures, and controller checkpoints so bad attempts can be thrown away.
27. Manageroo does not implement or own a multi-finding ClawPatch queue. That runtime is the standalone `clawpatch-supervise` project, installed and versioned independently. Manageroo can plan or invoke it through an argv-only optional adapter and can verify its external proof at the current Git HEAD. Supervisor behavior, checkpoint compatibility, process control, recovery, and native operating-system claims require proof in that standalone project. Manageroo-owned supervisor virtual environments use a separate stdlib-only console-entry gate solely to coordinate direct queue lifetime with package updates; it does not implement queue behavior.
28. Recoverable worker jobs, plan review, and review repair have no separate fixed attempt cap by default. Pre-version project configs containing the exact old generated `2/4/2` caps use the current unlimited phase defaults in memory without rewriting the file; configs marked `policy_version = 2` preserve explicit caps. The configured whole-run worker-call budget is durably persisted for normal runs and survives `run --continue`. It counts each real provider launch, including provider fallback attempts. Elapsed-runtime budgeting is enforced for the current process and clamps worker timeouts to remaining time, but elapsed runtime is not accumulated across a stopped process and later continuation.
29. Old incomplete runs created before outcome-specific proof bindings may block under the stricter completion policy instead of being grandfathered into `COMPLETE`. Restarting such work under the current proof contract is safer than silently preserving weaker evidence semantics.
30. The package is a source implementation. It is not installed in any product repository until the included installer and project initialization are run there.
31. Missing, duplicate, ambiguous, or failing outcome-specific proof bindings block completion. Duplicate gate-result IDs within one lane and conflicting results for the same gate across regular and demonstration lanes also fail closed. Observable user journeys, browser flows, authentication, security, deployment, and visual outcomes require matching demonstration-lane evidence rather than generic test success.
32. Manageroo bounds its own capability capsule and applies an ephemeral profile-scoped discovered-skill catalog filter to Codex workers. Generic third-party agent CLIs may still advertise additional provider-owned global capabilities before reading Manageroo's packet when that provider offers no equivalent per-process catalog control.
33. Installed host/plugin skills and repository-local skills are trusted instruction inputs, not hostile-code sandboxes. Manageroo validates and bounds their files and keeps controller scope/role/sandbox rules authoritative, but operators must still vet third-party skills before installation.
34. Skill support files are included in durable tree hashing and text-file UTF-8 safety validation, and selected trees are rehashed before every concrete provider launch, but only the selected `SKILL.md` entrypoint is injected automatically. A selected skill may direct the worker to read its validated support files from the recorded source path when needed. Manageroo does not provide a hostile-filesystem sandbox for operator-installed skills.
35. Transactional worker launch snapshots repository-local Git metadata in memory so unauthorized changes can be restored. Restoration materializes and verifies a sibling tree before a recoverable rename, fsyncing file data and directory entries where the platform supports it and retaining the live tree as a backup until the replacement verifies. The snapshot fails closed above its explicit entry, file, or aggregate-byte limits; unusually large Git directories must be compacted or handled in a disposable external boundary before Manageroo workers can run.
36. Manageroo installs Codex continuity hooks for active-objective capture, explicit local-tool scope checks, and premature-stop continuation. The prompt hook never blocks the operator. Explicit stop, pause, or wait language places the saved objective in a paused state: the stop hook allows the turn to end normally, tool use is denied, and questions do not reactivate the work. An explicit resume or an operator reaffirmation such as `I told you what to do next` restores the saved objective; a clear new work command replaces the paused backlog instead of silently reviving it. Reaffirmed stop or wait instructions remain paused. Explicit cancel/replace language and unambiguous natural corrections such as `No, use this instead` supersede unfinished work; actionable active follow-ups are additive while side questions remain conversation. The current repository is context rather than an implicit permission wall. External targets remain available unless the operator wrote an explicit exclusion or `only` boundary; those explicit limits are enforced for supported mutations. Routine prompt capture and successful tool checks emit no output or prompt context. Exact objective text stays in private state and is reinjected with compressed control wording only at session, subagent, or compaction recovery. Premature-stop recovery contains only a bounded current-task excerpt and the completion line. Supported local tools can be checked, but hosted or opt-out tools may bypass the local tool-hook path. Controlled runs remain the stronger isolated worker boundary.
37. Manageroo is not a hostile-code sandbox for the operator-facing agent or other same-user processes. Use the host workspace policy, managed container, separate operating-system identity, or disposable machine when that isolation is required.
38. Native project-memory and run-artifact evidence inputs require descriptor-relative, no-follow traversal and must be regular files with exactly one hard link. These providers fail closed when descriptor traversal is unavailable. Multiply linked files are rejected because filesystem containment cannot prove that their other directory entries remain inside the trusted evidence root.
39. Reuse conformance is enforced from exact operator directives through the reuse report, plan binding, implementation packet, independent review, and final report. Manageroo can block omitted, reclassified, changed, custom, or declared-substitution paths; semantic equivalence still depends on the configured proof gates and review evidence. It does not call substitute-specific tests proof that a named source was reused.
40. Manageroo controlled runs receive the explicit brief supplied to the run and do not scrape unstable Codex transcripts. The host continuity layer separately retains the current session's unfinished operator messages in private state and injects that active objective after follow-ups, resume, and compaction. Exact-task runs still accept explicit source, target, exclusion, and proof fields without transcript scraping.
41. Intent conformance protects the operator's request from worker drift. It is not permission for Manageroo to reject a newer operator instruction. A changed brief supersedes the saved run automatically; it does not silently rewrite already locked artifacts in place.
42. `MANAGEROO_EXECUTION_MODE=structured-worker` separates Manageroo-owned schema workers from operator continuity hooks. It is a behavior-selection seam, not a credential or hostile-process boundary; controlled-run sandbox, workspace, scope, and proof controls remain authoritative.
43. `doctor`, `ready`, and `stack-doctor` are environment, run-configuration, and optional-stack diagnostics. Their green results do not approve a release. Only a successful `release-ready` result is the final operator handoff, and that handoff still does not deploy production.
44. “Always active” means event-driven Codex hooks, not a resident daemon. Codex requires the operator to review and trust a new or changed hook set once through `/hooks`; Manageroo cannot honestly bypass or infer that security decision.
45. `manageroo update` uses the complete source folder recorded at install time or an explicit extracted current release supplied with `--source`. It does not silently download or execute a mutable remote branch. If that source is unavailable, the operator must provide current release bytes.
46. Guided uninstall automatically removes only components whose Manageroo ownership is proven. Shared or ownership-unproven Codex, GBrain, GitNexus, AUTOREVIEW, Clawpatch, Obsidian, package managers, and host tools are listed and preserved; user-edited skill trees are also preserved.
47. `manageroo benchmark` is a deterministic controller microbenchmark. Its token count is the documented character-based estimate, not provider billing data. It makes no model calls and therefore cannot prove that a probabilistic model writes better code. A useful live A/B needs repeated matched runs, blinded outcome scoring, and actual provider usage records.
